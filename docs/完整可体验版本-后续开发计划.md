# 灵体水獭 MVP：完整可体验版本后续开发计划

> **历史文档，已停止作为当前路线图。** 本文记录 2026-08-14 的单水獭、水面体验收敛计划。当前产品已调整为鹿禅、tata、飞儿三角色与三圈社区结构；“水下/水面/漂浮物”状态体系已经废弃。当前产品方向见 `docs/three-circle-world-and-community-linkage-v1.md`、`docs/three-agent-character-and-voice-v1-migration.md` 和 `README.md`。本文中的已完成状态、排期和最终门槛不得用于当前发布判断。

更新日期：2026-08-14

## 1. 当前状态结论

当前项目是“主要功能代码已经搭建，但完整运行链路尚未闭合”的工程原型，还不能作为完整可体验版本交付。

已经完成的代码包括：

- React/Vite 水面界面、统一灵体水獭图片和四种场景样式；
- 邀请码、匿名会话、对话、模式切换、行动、回访、导出和删除接口；
- 硬风险规则、结构化信号、五维内部状态、确定性政策路由和高风险静态响应；
- DeepSeek/OpenAI-compatible 模型网关和无密钥时的本地降级；
- 每轮情绪状态存储、相邻轮次定性变化和水獭周围飘字代码；
- 无数据库内容验收台、安全语料、单元测试和内容验收测试；
- Postgres/Prisma 数据模型、30 天清理任务、Caddy 配置和研究文档。

目前实际缺口包括：

- 当前可访问的是内容验收台，不是水獭正式体验；
- 正式体验受邀请码和数据库阻塞，本机没有可用 Postgres 与环境配置；
- 运行中的本地服务可能没有加载最新代码，页面与 API 版本不一致；
- 未配置真实模型密钥，本地关键词算法不能可靠理解自然语言；
- 内容验收台没有复用正式水獭界面，无法直观看到场景、数值和飘字联动；
- 当前状态是逐轮独立估计，尚未实现可靠的时间平滑和连续变化解释；
- Postgres 集成测试和完整浏览器 E2E 没有在真实环境执行；
- 本地目录尚未连接 Git 仓库，缺少稳定的版本发布流程。

## 2. 完整可体验版本定义

完整可体验版本必须同时提供两种运行方式：

1. 演示模式：无需数据库、邀请码和模型密钥，一条命令进入真实水獭界面，用于快速检查场景、对话、情绪值和飘字。
2. 完整模式：连接 Postgres 和真实模型，覆盖匿名准入、持久化、多轮对话、行动、回访、导出和删除。

两种模式必须使用同一套核心界面和支持引擎，禁止再出现“验收台表现正常，但正式产品无法体验”的割裂状态。

## 3. 后续任务群

### G11｜Git 仓库与版本基线（0.5 人日，P0）

任务：

- 确认目标 GitHub 仓库，不与个人笔记仓库混用；
- 克隆目标仓库或在用户确认后初始化当前目录；
- 检查 `.gitignore`，排除 `.env*`、密钥、`node_modules`、构建产物和运行日志；
- 提交当前代码、测试、视觉资产和本文档；
- 建立开发分支、草稿 PR 和最小 CI：类型检查、单元测试、构建。

验收：

- 新环境可以从仓库完整检出；
- 仓库中不存在真实密钥和本地数据库数据；
- CI 可以独立运行类型检查、测试和构建。

### G12｜一条命令的水獭演示模式（1.5 人日，P0）

任务：

- 新增 `npm run dev:demo`；
- 演示模式直接进入正式 `App` 水面界面，不要求邀请码或 Postgres；
- 使用内存会话保存当前浏览器生命周期内的消息、模式和行动；
- 页面醒目标注“本地演示，不保存数据”；
- 无模型密钥时标注“规则模拟”，有密钥时标注实际模型；
- 内容验收台保留为研究者调试工具，但不再作为产品体验入口。

验收：

- 新开发者安装依赖后，一条命令、两分钟内看到水獭；
- 能连续完成“倾诉 → 陪伴回复 → 同意整理 → 一个行动”；
- 演示模式关闭后不留下用户对话数据。

### G13｜情绪变化与飘字完整链路（2 人日，P0）

任务：

- 将当前五维状态统一为：效价、唤醒度、压力负荷、认知过载、支持需求；
- 为状态增加上一轮比较和最小变化阈值，避免轻微噪声触发飘字；
- 增加短期平滑：最近三轮加权平均，24 小时后失效；
- 正式界面只显示定性飘字，不显示伪精确分数；
- 演示/验收模式显示五项数值、变化方向、信号来源和置信度；
- 每轮最多显示三条飘字，约 6 秒淡出；
- 用户可关闭情绪反馈，减少动态效果时改为静态标签；
- `high/imminent` 强制关闭数值、飘字和沉浸背景。

验收样例：

- “任务全堆在一起，我不知道先做哪个”应明显提高认知过载；
- 后续“现在理清楚一点了”应降低认知过载并出现“思绪清楚了一点”；
- 相同输入重复发送不应产生无意义的大幅波动；
- 高风险输入不得出现情绪标签或文学化反馈。

### G14｜本地规则降级与真实模型接通（1.5 人日，P0）

任务：

- 扩充本地降级词组、否定词、程度词和组合表达；
- 将“关键词命中”升级为可审计的规则信号，返回命中证据；
- 配置并验证一个真实 OpenAI-compatible 模型；
- 启动时验证模型 ID、JSON 模式、超时和用量元数据能力；
- 模型不可用时在界面明确说明正在使用规则模拟；
- 用冻结样本比较模型与降级算法的状态差异。

验收：

- “不知道先做哪个”“脑子转不动”“事情堆在一起”等常见表达可被降级算法识别；
- 模型输出为空、格式错误或超时时，界面可恢复且不创建行动；
- 真实模型和本地降级的来源在验收模式中清晰可见。

### G15｜完整环境启动与诊断（1.5 人日，P0）

任务：

- 提供 Windows 可执行的环境预检命令；
- 检查 Node、Postgres、数据库迁移、端口、环境变量和模型连通性；
- 支持 Docker Postgres 和本机 Postgres 两种启动说明；
- 提供一条完整初始化流程：迁移、种子、邀请码、服务启动；
- 启动时打印两个明确入口：演示模式和完整模式；
- 避免旧进程继续占用端口，并在页面展示前后端构建版本。

验收：

- 缺少 Postgres、密钥或配置时给出明确中文提示；
- 页面与 API 显示相同版本号；
- 重启后完整模式可以恢复会话、行动和回访。

### G16｜正式水獭体验补全（1.5 人日，P1）

任务：

- 在邀请码页提供克制的水獭轮廓预览，让用户确认进入的是水獭产品；
- 登录后保证水獭、当前模式、当前场景和对话同时可见；
- 将飘字限定在水獭场景区域，不遮挡聊天和操作按钮；
- 增加情绪反馈开关和“AI 的暂时理解，可能不准确”说明；
- 手机端验证软键盘、飘字位置、行动卡和安全状态；
- 模式切换、行动确认和回访均提供明确成功状态。

验收：

- 首次进入五分钟内可以看到水獭并完成一轮对话；
- 用户能区分陪伴、整理和安全响应；
- 手机和桌面均无主要内容遮挡。

### G17｜真实集成与端到端验收（2 人日，P0）

任务：

- 在独立 Postgres 测试库运行全部集成测试；
- 增加演示模式 E2E 和完整模式 E2E；
- 覆盖首次进入、普通倾诉、状态变化、飘字、模式接受/拒绝、行动、回访和删除；
- 验证刷新恢复、重复请求、并发请求、模型超时和数据库短暂失败；
- 运行 120 条安全回归，并人工查看高风险页面；
- 将测试结果输出为可读验收报告。

验收：

- 类型检查、单元测试、集成测试、构建和核心 E2E 全部通过；
- 不再以“测试被跳过”作为通过；
- 高风险样本没有水獭沉浸、飘字、行动建议或诊断结论。

### G18｜局域网试用交付（1 人日，P1）

任务：

- 实际验证 Caddy、本地 HTTPS、研究设备 CA 和 Cookie；
- 验证邀请码生成、匿名导出、30 天清理、备份和恢复；
- 增加服务版本、启动检查表、停止检查表和故障记录；
- 完成五人内部预试后再生成正式邀请码。

验收：

- 局域网研究设备可访问，其他网络不可访问；
- 服务重启和短暂故障不会产生重复数据；
- 五名预试者均能独立完成完整核心流程。

## 4. 建议排期

总工作量约 11.5 人日，建议分两周完成：

### 第 1 周：先做到“看得见、跑得通”

- 第 1 天：G11 仓库基线、G12 演示模式骨架；
- 第 2 天：完成 G12，直接进入真实水獭界面；
- 第 3–4 天：G13 情绪变化、数值面板和飘字联动；
- 第 5 天：G14 降级算法和真实模型接通。

周验收：无需数据库即可连续体验水獭、对话、状态变化、飘字和一个行动。

### 第 2 周：做到“完整环境可重复交付”

- 第 6 天：G15 环境预检、Postgres 和完整启动；
- 第 7 天：G16 正式界面与手机体验；
- 第 8–9 天：G17 集成、E2E 和安全回归；
- 第 10 天：G18 局域网交付和内部预试修复。

保留约 1.5 人日缓冲，只处理阻塞问题，不增加功能。

## 5. 最终完成门槛

只有同时满足以下条件，才可以称为“完整可体验版本”：

- 一条命令能够打开带水獭的演示版本；
- 完整模式可以通过邀请码进入并持久化会话；
- 至少三组连续输入能够产生合理、可解释的情绪变化；
- 用户能够看到定性飘字，研究者能够看到内部数值和来源；
- 高风险输入关闭所有沉浸反馈并进入直接支持；
- 真实模型与本地降级均有明确状态提示；
- Postgres 集成测试和核心浏览器 E2E 实际执行并通过；
- 新机器按照文档可以完成安装、启动、测试和停止；
- 代码已经提交到目标 GitHub 仓库并通过 CI。
