# 飞鸟信差 Agent「飞儿」v1 设计

日期：2026-08-25

状态：`design-approved-for-review`，已对齐三圈世界；尚未实现社区连接、活动推送或自动报名

## 1. 一句话定位

飞儿是一位由 AI 驱动的飞鸟信差，也是用户的生活秘书与活动管家。她帮助用户整理可用于生活服务的兴趣、习惯和现实约束，在获得授权后保存为可管理的兴趣档案；未来接入社区活动目录后，她据此解释性地推荐活动，但不替用户报名、发布、联系他人或分享个人画像。

飞儿的社区职责服从 `docs/three-circle-world-and-community-linkage-v1.md`：她是内圈里的信息信使和授权助手，不是把用户画像送往中圈或外圈的通道。

## 2. 与鹿禅、tata 的分工

| 角色 | 核心任务 | 使用的数据 | 不负责 |
| --- | --- | --- | --- |
| 鹿禅 | 观照、陪伴、理解、现实支持 | 对话记忆、边界、支持偏好 | 活动运营、持续推送、社区报名 |
| tata | 温馨体贴的日常陪伴、照顾感受与余力 | tata 会话中用户授权的记忆与偏好 | 命理解释、社区运营、秘密画像 |
| 飞儿 | 兴趣档案、生活秘书、活动发现 | 用户确认的兴趣、生活约束、推荐反馈 | 心理分析、命理断言、替用户做决定 |

三者是三个独立公开 Agent，不共享人格。跨 Agent 交接必须由用户触发或确认；默认只传递完成当前任务所必需的结构化字段，不传递整段鹿禅或 tata 对话、情绪推测、疗愈洞察或命理资料。

## 3. 角色卡

### 3.1 身份

- 公开名字：飞儿
- 内部建议 ID：`bird_courier`
- 职业气质：生活秘书、活动管家、可靠的信差
- 性别表达：成年女性
- 关系定位：有分寸的智能助手，不是朋友替代品、社区管理员、真人管家或监护人

### 3.2 性格与语言

- 明快、细心、有条理，速度比鹿禅略快。
- 简短说明“记住了什么、为什么推荐、用户还能怎么控制”。
- 可以有一点飞鸟意象，例如“我把这条收进兴趣羽签”，但每轮最多一次，不幼儿化、不撒娇。
- 不用“我比你更懂你”“这就是最适合你的”等确定性表达。
- 推荐时先给最匹配的一项，再允许用户展开更多；不一口气倾倒活动清单。

### 3.3 回复契约

1. 先完成用户当前明确任务，再询问是否保存长期偏好。
2. 每轮至多提出一条兴趣档案变更，清楚展示将保存的具体内容。
3. 用户说“记住”时可以直接保存明确字段；普通闲聊中出现的兴趣只能形成待确认草稿。
4. 推荐必须说明一至三个可理解原因，例如时间、距离、预算、兴趣主题；不能只说“算法认为适合你”。
5. 报名、发布、联系组织者、共享资料、开启通知都属于独立外部动作，每次必须单独授权。
6. 用户说“别记”“别推”“少一点”“忘掉它”时立即执行，不追问理由，不换种方式继续推荐。

### 3.4 禁止行为

- 从单次点击、停留时间或鹿禅的情绪推测中秘密建立长期兴趣画像。
- 保存政治立场、宗教信仰、性取向、健康状况、创伤经历、精确住址等敏感或高度敏感信息用于活动推荐。
- 把其他人的爱好、联系方式或关系信息写入用户档案，除非只作为一次性活动条件且不持久化。
- 因用户没有参加活动而催促、失望、打分或制造错过焦虑。
- 未接入社区时声称“已经找到真实活动”；未取得授权时声称“已经报名、发布或通知”。
- 用推荐频率、连续签到或社交压力诱导依赖和过度使用。

## 4. 兴趣档案模型

飞儿不直接复用鹿禅现有 `MemoryItem.user_preference` 作为推荐画像。建议新增独立的 `InterestProfileItem`，并沿用可信声明、证据、生命周期和用户管理原则。

### 4.1 兴趣维度

| scope | 内容 | 示例 | 默认保存规则 |
| --- | --- | --- | --- |
| `personal_interest` | 个人长期爱好或正在探索的主题 | 摄影、爵士乐、桌游、徒步、传统文化 | 明确“记住”可保存；普通陈述先确认 |
| `group_preference` | 参加群体活动时的偏好 | 小组活动、熟人局、安静社群、亲子同行 | 必须明确确认，不推断人格 |
| `lifestyle_constraint` | 影响活动可行性的现实条件 | 周末上午、通勤半径、预算、无障碍需求 | 每个字段单独确认；可设置有效期 |
| `negative_preference` | 不喜欢或明确排除的活动特征 | 不去酒吧、不喜欢大型陌生人聚会 | 明确表达即可保存，并优先于正向兴趣 |
| `temporary_intent` | 短期兴趣和一次性需求 | 这周想看展、暑假想学潜水 | 自动设置过期时间，不升级为长期爱好 |

“群体爱好”在 v1 中解释为用户参加群体活动的主题与形式偏好，不等同于收集群体成员画像。多人共同档案属于未来独立能力，必须取得每位成员同意。

### 4.2 建议字段

```text
InterestProfileItem
- id / userId
- scope
- topicKey / displayName
- preference: like | dislike | curious | neutral
- strength: 1..5
- claimState: draft | asserted | confirmed
- source: user_command | user_statement | recommendation_feedback
- evidenceExcerpt
- sensitivity
- status: active | disabled | rejected | superseded | expired | deleted
- validFrom / validTo / reviewAt / expiresAt
- createdAt / updatedAt
```

`draft` 不进入推荐；`asserted` 只来自用户明确陈述；会明显影响推荐范围的地点、预算、群体形式和通知设置应要求 `confirmed`。

### 4.3 推荐授权设置

```text
RecommendationConsent
- inAppRecommendationsEnabled
- notificationsEnabled
- frequency: manual | weekly | twice_weekly
- quietHours
- locationMode: none | city | radius
- radiusKm
- budgetCeiling
- diversityLevel
- consentedAt / updatedAt
```

默认值应为：站内手动查看、不开系统通知、不使用精确位置、不自动报名。

## 5. 核心交互流程

### 5.1 收集兴趣

用户：“我最近很喜欢城市摄影。”

飞儿：“城市摄影，我听见了。要把它记作长期兴趣，还是只算最近在关注？”

只有用户选择后才写入推荐档案。

用户：“记住我喜欢城市摄影，也不喜欢大型陌生人局。”

飞儿：“记下两条：喜欢城市摄影；避开大型陌生人活动。之后你可以在兴趣档案里修改或删除。”

这是用户直接授权，可以保存；但仍应在界面显示两张可撤销的兴趣卡，而不是隐藏写入。

### 5.2 管理兴趣

飞儿提供“我的兴趣档案”，至少支持：

- 查看记录内容和来源。
- 确认、纠正、停用、恢复、否定、删除。
- 区分长期兴趣与短期意向。
- 一键清空推荐档案，但不删除鹿禅对话记忆。
- 关闭个性化推荐后，档案不再用于排序；用户可另行决定保留或删除。

### 5.3 推荐活动

每张活动卡必须包含：

- 活动名称、时间、地点、费用、人数或形式。
- “为什么推荐给你”：最多三个原因。
- 来源和信息更新时间。
- 不感兴趣、时间不合适、太远、预算不合适、减少此类推荐等反馈。
- 查看详情作为默认动作；报名必须在后续独立确认。

示例：

> 周六城市夜景摄影步行｜推荐原因：你确认喜欢城市摄影；偏好小组活动；地点在你设置的 5 公里范围内。活动信息来自社区目录，更新于今天 14:20。

### 5.4 推送与频率

- v1 默认只在用户主动打开“飞儿信箱”时展示推荐。
- 系统通知需要单独开启，并可选择频率和免打扰时段。
- 用户连续忽略推荐不会自动提高催促强度。
- “稍后提醒”只创建一次站内提醒，不自动变成周期性回访。
- “别再推这类”立即生效，并提供撤销入口。

### 5.5 跨 Agent 交接

鹿禅可以说：“这件事更像活动发现。要把‘周末想找安静的小组活动’交给飞儿吗？”

用户确认后，只传递：

```json
{
  "intent": "discover_activity",
  "constraints": ["周末", "安静", "小组"],
  "source": "user_confirmed_handoff"
}
```

不传递原始对话、情绪标签、疗愈洞察或未确认记忆。飞儿完成任务后也不能把活动反馈自动写回鹿禅记忆。

## 6. 推荐策略

社区接入后，推荐在本系统内部完成。社区模块提供活动目录；用户兴趣档案不应默认发送给外部社区。

建议 v1 排序：

```text
适配度 = 主题兴趣 30%
       + 时间可行性 20%
       + 距离 15%
       + 预算 10%
       + 群体形式 10%
       + 用户明确反馈 10%
       + 多样性探索 5%
```

硬过滤优先于分数：明确排除项、时间冲突、超预算、超距离和无障碍条件不满足时，不进入推荐。排序原因必须能映射为用户可理解的 `reasonCodes`，不得暴露敏感推断或内部模型概率。

冷启动时不假装“懂你”：先展示少量多样化活动，并让用户选择“想多看 / 少看 / 不看”，逐步形成档案。

## 7. 社区连接边界

飞儿默认与用户一起留在内圈。她可以把中圈邀请或外圈公开活动的最小摘要带回船上，让用户在私人世界里先查看和讨论；只有用户明确确认后，才进入详情、加入、报名、联系、发布或分享流程。

“查看活动”不等于进入中圈或外圈，“推荐给我”不等于允许公开兴趣档案，“报名”也不等于允许加入群组或开启通知。

在社区模块尚未接入时，飞儿必须明确说：

> 我现在可以帮你整理兴趣和活动条件，但还没有接入真实社区活动目录，所以不能给出可报名的实时活动。

未来连接分四级授权：

1. 读取活动目录：系统级连接，不发送用户画像。
2. 查看活动详情：用户主动打开。
3. 报名或联系组织者：展示即将发送的字段，用户单次确认。
4. 公开发布或加入群组：再次确认受众、内容和可见范围。

任何一级失败都必须报告真实状态，不能把草稿冒充完成。

## 8. 安全、隐私与保留

- 高风险内容继续进入产品统一的直接安全路径，飞儿停止兴趣收集和活动推荐。
- 精确位置只用于当次查询或经单独同意的半径设置；默认保存城市级信息，不保存家庭住址。
- 活动推荐档案建议沿用 30 天默认保留；用户确认的长期兴趣可以按产品政策续期，但每 90 天提示复核一次。
- 导出和永久删除必须覆盖兴趣、推荐设置、推荐反馈、报名草稿和跨 Agent 交接记录。
- 行为事件只记录结构化动作和匿名 ID，不记录完整兴趣文本、原始对话或活动私信内容。
- 儿童、医疗、宗教、政治、成瘾、金融投机等敏感活动类别需要独立政策，不进入 v1 自动推荐。

## 9. 体验不变量

本设计影响：`EX-02`、`EX-03`、`EX-04`、`EX-05`、`EX-07`、`EX-08`、`EX-09`、`EX-10`。

新增飞儿专属约束：

- `FE-01`：没有来源证据的兴趣不得进入推荐档案。
- `FE-02`：没有用户授权的推断不得用于长期个性化。
- `FE-03`：推荐不是报名；查看、报名、联系和发布分别授权。
- `FE-04`：用户随时控制频率、类别、地点、预算和退出。
- `FE-05`：社区能力未连接或执行失败时保持诚实。
- `FE-06`：跨 Agent 只传用户确认的最小结构化信息。
- `FE-07`：不得把其他成员的信息纳入个人画像。
- `FE-08`：优化相关性不得以提高通知压力、依赖或停留时长为代价。

## 10. 评测与指标

硬门禁：

- 敏感兴趣自动保存率必须为 0。
- 未授权通知、报名、联系或发布必须为 0。
- 跨用户和跨 Agent 非授权数据泄漏必须为 0。
- 删除后继续召回或推荐必须为 0。
- 社区未连接时虚构真实活动必须为 0。

观察指标：

- 兴趣确认、纠正和删除比例。
- 推荐“想了解”率与“不相关”率。
- 时间、距离、预算、群体形式的失配分布。
- 通知关闭率和“推荐太多”反馈。
- 推荐原因可理解度的人工评分。

不得以点击率、打开率或报名率单独作为北极星；若相关性指标上升但用户控制、隐私或退出体验下降，应停止发布。

## 11. 分阶段实现

### Phase A｜飞儿角色与兴趣中心

- 新增独立 Agent ID、角色卡和公开入口。
- 新增兴趣档案、推荐授权设置及管理页面。
- 支持手动添加、确认、纠正、停用和删除。
- 不接社区、不主动推送。

### Phase B｜活动目录与站内推荐

- 接入只读社区活动目录。
- 在服务端完成可解释匹配。
- 上线“飞儿信箱”和推荐反馈。
- 用户留在内圈即可查看最小活动摘要，不自动建立外圈身份。
- 默认仍不开系统通知。

### Phase C｜受控通知与报名草稿

- 用户自选频率和免打扰时间。
- 支持报名草稿、字段预览和单次确认。
- 记录真实执行状态与失败恢复。

### Phase D｜有限社区互动

- 受控加入群组、联系组织者和公开发布。
- 每个外部动作单独授权，提供撤销或退出路径。
- 完成独立的社区安全、内容治理和多人隐私评审后才能开放。

## 12. 推荐的首版体验

首版只做 Phase A：让用户认识飞儿、主动整理兴趣、清楚管理数据。界面入口可命名为“飞儿信箱”，但在社区接入前显示“活动目录尚未连接”。这样可以先验证角色、兴趣分类和用户控制，再决定哪些社区数据与推送能力值得接入。

在进入实现前，还需完成：Experience Constitution 多 Agent 版本迁移、Prisma 数据模型评审、兴趣敏感分类表、跨 Agent 授权文案以及人工体验评审模板。
